# AGENTS.md

Repo-source facts that structure and naming cannot carry. The exec-family `timeoutMs` prefix and the `raw_body`/plain-text contract are in README.md ("Exec-family timeout prefix").

## Runner and daemon liveness

- **Runner recovery.** The daemon exits on purpose and this process brings it back. It self-recycles when idle (`self-recycling after 3600000ms fully idle` in `~/.agentplug/daemon.log`) or over its wasm memory ceiling, then hands off to a freshly downloaded runner build; a cold start costs tens of seconds of wasm compile. `ensureSpoolRunnerRunning` recovers a dead daemon. Liveness is judged by `status.json`'s `pid` via `process.kill(pid, 0)` (`liveDaemonSweepsProject`), never by heartbeat age. `daemonBootGraceActive` covers a fresh `daemon_boot_ts` in `~/.agentplug/daemon-status.json` that has not swept a project yet. The ensure spawn is idempotent, so `ENSURE_INTERVAL_MS` (2 s) and `ENSURE_LEASE_MS` (3 s) stay small. `startRunnerWatchdog` re-checks every root every 5 s (opt out `GM_MCP_RUNNER_WATCHDOG=0`). No `status.json` means never swept: that is registration, not a liveness verdict.
- **Dead-daemon pre-flight.** `daemonNotRunning` runs before `publishSpoolRequest`, since a ticket written into a dead spool waits unclaimed. A stale heartbeat gets one `ensureSpoolRunnerRunning` plus `DAEMON_START_GRACE_MS` (15 s); only then does the call return `error: daemon-not-running`, unwritten. It does not fire with no `status.json`, inside `daemonBootGraceActive`, or during `runner_update_in_progress`. `GM_MCP_DAEMON_PREFLIGHT=0` bypasses it.

## Dispatch wire and polling

- **Glob filters.** `codesearch` and `grep` read `glob`, `path_glob`, `include`, `exclude_glob` and `exclude_globs` as a string or array of strings; the wasm matches them (`!` excludes, `{a,b}` brace lists work). `withGlobFiltersCoerced` trims entries and fails on a non-string or non-array value, an empty string, an empty array or a blank entry. Never join an array into one brace glob: that mangled entries containing `,`/`{`/`}` and refused `!`. The wasm sets `glob_matched_no_files: true` when nothing matches.
- **Waited dispatches.** A reply landing after `DISPATCH_WAIT_DISCLOSED_AT_MS` (250 ms) carries `dispatch_waited_ms`. `codesearch` `timeout_ms` is a scan wall-clock budget (regex default 20000) enforced in the wasm; its overrun reply is `timed_out: true`, `exhaustive: false`, `budget_ms`.
- **Timeout prefix sync.** `TIMEOUT_MS_PREFIX_LINE` mirrors rs-plugkit `strip_timeout_ms_prefix_directive`: skip leading whitespace; the first line must start with `timeoutMs=` or `timeout_ms=`. Keep the two in sync.
- **Instruction hash assertion.** `deliveredInstructionHashByOwner` caches, per (project root, `session_id`), the hash of the `instruction` prose last returned. `withAssertedInstructionHash` asserts it on the next `instruction` dispatch, so gm can answer `instruction_unchanged: true`. The cache is process-lifetime, so a restarted server resends the prose.
- **Poll budgets.** `pollTimeoutMs` computes the requested budget, not what the daemon enforces. An explicit `timeout_seconds` wins. Otherwise an exec body starting with `timeoutMs=<ms>` requests that plus 5 s (never under 120 s), because the daemon kills the child tree at its wall-clock `timeoutMs` and answers `exec_timeout`. A wrapper-injected prefix follows the poll budget minus 5 s, floored at 300 s (`EXEC_DEFAULT_LIMIT_SECONDS`) and capped at 900000 ms (`EXEC_HARD_CEILING_MS`). A poll without a prefix waits 120 s; a `resume_task` poll has only `timeout_seconds`. Every poll is capped at 600 s (`GM_MCP_POLL_TIMEOUT_CEILING_MS` overrides). A timeout reports requested and applied budgets; it neither cancels nor republishes.
- **A timed-out dispatch still answers.** `timeoutReply` reads each diagnostic alone, so a throwing one is dropped, never the resumable task; `npm run verify-build` fails when one cannot be built.
- **Exec output envelope.** `unpackExecOutputEnvelope` parses the `data` JSON string before cleaning, so `stdout`, `stderr` and `result` keep their own 16000-char cap (`EXEC_OUTPUT_FIELD_TRUNCATE_AT`). The marker names `result_file` (set when a field exceeds 2000 chars) or, for an older daemon, the out-file.
- **Spool reads.** Symlinks are refused before open; the opened file is checked by dev and ino, never by a `/proc` or `/dev/fd` path (`dispatch.js`). Stale response files are pruned at most once per `SPOOL_PRUNE_EVERY_MS`; `reclaimLockByRename` lets only the rename winner own a reclaim.
- **Alias fields are per handler.** `git_reset` reads `ref|rev` and `mode|hard`; `git_revert` reads `ref` alone, so a `rev` alias is silently ignored (`verb-table.js`).

## Response compaction

- **Two stages.** In `src/response-compact.js`, `cleanResponse` is lossless housekeeping: it strips opaque ids, drops empties except the answer lists in `EMPTY_LIST_IS_THE_ANSWER_KEYS` (an empty `candidates` prints `[]`), and truncates prose at `LONG_TEXT_FIELD_TRUNCATE_AT` (400 chars). A plain-text-body verb (`isPlainText` in `dispatch.js`) gets `PLAIN_TEXT_OUTPUT_INLINE_MAX` (32768, read once from env), because its whole response is the script's output; raising the generic cap would un-truncate `instruction`'s prose. `fs_read` gets `FILE_READ_INLINE_MAX` (65536). `max_chars` overrides the defaults.
- **Full response.** `full_response: true` bypasses cleaning, data flattening, native-envelope decoding and wire compaction; the response file stays bounded by the 4 MiB read limit. Exec-family fields keep `EXEC_OUTPUT_FIELD_TRUNCATE_AT` and `result_file`. Default responses keep `dispatch_id` evidence; `request_fingerprint` is kept only in full responses.
- **Failures are not compacted.** Compaction runs only when the response has no failure. Default responses omit `stdout` from a fault when it is a nonempty JSON object deeply equal to the containing fault object; the response names the original spool file.
- **Field decisions.** Dropped: `route_hint`, `reply_hash`, `orient_nouns`; `supply_chain_scan` when it has no findings (else `warnings` capped at 8 with `warningsOmitted` beside `warnCount`); `session_owner_before_this_dispatch` unless `session_mismatch` is true. Collapsed to counts: `codeinsight_overview`, `codeinsight_start` (to `{ready: true}`; whole when not ready), `config_changed` (newest transition, 3 keys), `dream_rsi_strategy`, `dream_rsi_replay`. Excerpted: row and hit prose in `ready_wave`, `prd_items`, `mutables_pending`, `recall_hits` (top 4), `bm25_hits`, `vector_hits` (top 20 each). `id`/`key`/`status`/`session_id`/`verb` are exempt so a row stays addressable. Codesearch's `bm25_hits`, `vector_hits` and `commits` stay as named channels even when empty. Kept whole: `instruction`, `phase`, `ok`, `session_id`, `instruction_hash`, `policy_hash`, `discipline_policies` (only when the policy hash moved), and every count.
- **Count mode.** Wire compaction of count results requires explicit `ok: true`, `exhaustive: true`, no failure or partial diagnostics, and same-length exact `path:count` parity between `output` and structured `counts`. Only the derived `output` is omitted.
- **Phase history and receipts.** `phase_history` keeps its newest five transitions in source order with retained/total counts. Committed `git_commit`/`git_finalize` successes keep at most five `excluded` and `excluded_but_dirty` examples. Failures, refusals, uncommitted receipts and `full_response: true` bypass this.
- **Zero hits.** A search reply with no hits is annotated `zero_hits_is_not_a_finding` unless the scan covered its files (`searched_zero_files`): "0 hits" and "code absent" are identical bytes.

## Working directory, sessions and dev sync

- **Cold projects.** A non-git cwd is rooted on itself (`projectRootFor`) and the daemon registers and sweeps it like any project. First claims on cold projects are slow under a shared daemon; the timed-out note points at `resume_task`.
- **Plain-text ownership.** Plain-text replies carry a byte-zero `gm_session_id=<owner>\n` header before the timeout directive; the guest advertises `gm_session_header_version: 1`. MCP probes with a safe JSON `phase-status` and caches only a coherent result bound to project, daemon boot, PID and GM hash; every nonempty pool slot must agree. Legacy or unverified guests get the original text with `owner_transport: legacy-unverified` or `unverified`; nothing is retried.
- **In-flight count.** `inflightDispatchCount()` feeds the exit and signal records, the self-update check (`deferred-dispatch-inflight`) and the runner-swap signal (`dispatch-in-flight`). A process quitting mid-dispatch strands the spool ticket it wrote. A deferred self-update is retried seconds later, up to 4 times per trigger (`self-update-defer-retry`, then `self-update-defer-retry-exhausted`); the retry runs the same check, so `GM_MCP_SELF_UPDATE_INTERVAL_MS` still governs how often anything is fetched.
- **Cwd-less dispatch never guesses.** The root comes from the `cwd` argument, then `GM_MCP_DEFAULT_CWD` (only when it is a git toplevel), then the server cwd only when it is a git toplevel; otherwise the reply is `error: cwd-required`. No harness variable is read: the HTTP singleton inherits the environment of whichever session spawned it. The stdio relay supplies the per-session default: when its own launch cwd is a git toplevel (`launchRootDefault`, `src/stdio-relay.js`) it adds that `cwd` to a `tools/call` whose arguments carry none.
- **Dev sync.** `runDevSync` syncs the parent before its submodules, because the parent's `--ff-only` merge moves submodule pins; a submodule fast-forwards only when on `main`. `maybeStartDevSync` never blocks a dispatch: the child is detached and unref'd, and one sync starts per 10 minutes (`SYNC_INTERVAL_MS`) across all roots.

## Process resilience and diagnostics

- **Stdio never exits on errors.** `keepServingOnAsyncFailure` (uncaught, unhandled, stdin and stderr errors) and `surviveClientGone` (stdout EPIPE, stdin end) record and continue. A dispatch is a spool ticket someone waits on. Each stdout error code is recorded once.
- **Signal and exit records.** `logSignalExits` records SIGINT, SIGTERM, SIGHUP and SIGBREAK, then exits 0, so the exit status hides the signal; the `exit` record carries it, plus `uptime_ms` in `src/transport-guard.js`, which survives the repeat filter. A killed singleton leaves no `exit` record, because `logSignalExits` only sees signals a handler runs for.
- **Stdout guard.** `isJsonRpcFrame` checks that the first byte is `{` before parsing. Anything else is diverted to stderr as `stdout-write-diverted`.
- **Diagnostics.** `appendDiagnostic` writes each record to stderr and, unless repeat suppression holds it, to `logFilePath()` (`gm-mcp-server.log`, rotated to one `.1` past 2 MB by `src/server-log.js`). An identical event and fields within 60 s are counted, not written (ignoring `ms`, `inflight`, `dispatches_inflight` and `pid`), and the next write of that key is preceded by `repeat-suppressed`. The host discards stderr, so the file is the durable record.

## HTTP transport and singleton

- **Singleton is opt-out.** One shared server per machine, keyed by port. `httpSingletonEnabled` (`src/singleton.js`) is off only when `GM_MCP_NO_HTTP_SINGLETON` or `GM_MCP_HTTP_SINGLETON_OFF` is set to anything but `0`/`false`/`no`/`off`. An agent host registered with the HTTP url never launches this server, so with nothing listening its connection fails and every gm tool is absent. A stdio session serves in-process over the spool by default (`main` in `src/index.js` runs `createServer` on stdio; `dispatch.js` publishes each request to `.gm/exec-spool`). Only `GM_MCP_RELAY=http` makes a stdio session relay to the singleton (`serveStdioRelay`, `src/stdio-relay.js`, `stdioRelayTarget`): a failing relay call is retried after 250 ms and 1 s while the error is a connection error (`TRANSIENT_CODES`), then once after `recover` restarts the singleton, then served by an in-process server over an in-memory transport (`createLocalFallback`). A codemode body that throws returns the count of gm replies that completed before the throw and their dispatch ids; their bodies are not replayed. `gm-mcp dispatch` seeds one awaited with `wait: false` (`src/cli.js`). `ensureHttpSingleton` trusts the health probe on the port over the state file (`gm-mcp-http.json`). The spawned singleton runs the bundle this process launched from (`launchedEntryPath`) and inherits `GM_MCP_NO_HTTP_SINGLETON=1`, so it cannot spawn a server on the port it already holds.
- **Supervisor.** `ensureHttpSupervisor` (`src/singleton.js`) spawns one detached, unref'd sibling per port that probes `/health` on a timer and reruns the start path when answers stop. Detached, because a caller-parented supervisor dies with the caller's tree. Opt-out: `GM_MCP_HTTP_SUPERVISOR=0`, which the child also inherits so restarted servers never arm a second supervisor. An HTTP-transport process arms it, and `ensure-http` arms it on every run. `runHttpSupervisor` runs in the foreground so a service manager can hold it. Spawns are claimed per port by `claimSpawn` (`wx` create); losers answer `claim-held` or wait for health. Liveness is the state file's `ts`, refreshed each pass and stale after `SUPERVISOR_STATE_STALE_MS` (60 s), not its pid. `supervisorToKeep` keeps a fresh claim's pid, else the newest start time; equal start times keep neither.
- **Instance registry.** Each HTTP-transport process registers in `<agentplugDir()>/gm-mcp-http-instance-<port>.json` (`recordHttpInstance`): pid, bundle version, entry path and the supervisor pid it armed. `registeredHttpPorts()` enumerates instance files, supervisor files and `gm-mcp-http.json`. `sweepHttpInstances()` runs in `ensure-http` and on every supervisor pass:
  - `reapDeadHttpInstances` drops all three files of a port whose server is gone.
  - `replaceBehindHttpInstances` retires a server whose `/health` version is behind this process's `BUNDLE_VERSION` (`versionBehind`) and starts a fresh one on the same port.
  - `reapOrphanedHttpInstances` stops one with no live supervisor, a provably dead parent (`parentPidOf`) and zero established connections (`establishedConnectionCount`). A null answer and any nonzero count are never reaped.
  A version replacement also stops that port's supervisor and re-arms it with `ensureHttpSupervisor({force:true})`. `ensureHttpSingleton` applies the same version test and retires a recorded pid that holds the port but answers no health check. A version-behind holder is retired only when `holderIsOwn` (its pid is the port's recorded instance or supervisor pid); a foreign holder is kept (`http-singleton-behind-kept`), so a squatted port is never killed or supervised.
- **Stateless transport.** No session id is issued; every POST builds a fresh server and transport (`serveStatelessMcpRequest`), because the SDK rejects a second request through one transport. Non-POST requests to `/mcp` get 405. `startHttpServer` records `http-listen-failed` with the errno `code` before rethrowing.
- **Protocol version.** After `initialize`, the SDK answers 400 to an `mcp-protocol-version` outside `SUPPORTED_PROTOCOL_VERSIONS` (SDK 1.30.0, `validateProtocolVersion`). `normalizeProtocolVersion` rewrites the header to `SUPPORTED_PROTOCOL_VERSIONS[0]` before the SDK reads it.
- **Supervision outside this repo.** `scripts/install-autostart.mjs` writes a managed block into `$HOME/beforestart` (boot) and `$HOME/crontab` (`@reboot` plus a minutely `ensure-http` guard), runs `ensure-http` once, probes `/health` first, and is idempotent. Reinstall: `node scripts/install-autostart.mjs`; uninstall: `--uninstall`; dry run: `--check`. Manual revive and status: `node ~/.gm-tools/gm-mcp-server.mjs ensure-http` and `http-status`. Guard log: `$HOME/logs/gm-mcp-autostart.log`.
- **Stale stdio images clear on client relaunch.** A stdio process never self-exits on staleness and no supervisor reaps it: its parent client holds stdin, and a self-exit would drop that client (`bundleDrift` refuses `no-handover` for every non-HTTP transport). `self-update-status` lists such an image as `stale` until its client relaunches.
- **Body cap and listen retry.** `readCappedJsonBody` counts bytes as they arrive, since Content-Length alone lets chunked bodies through. `EADDRINUSE` is retried until the listen deadline, with or without an adopted handle (`http-transport.js`).
- **Staleness is said once.** `/health` carries a `bundle` block (`running_version`, `running_sha256`, `installed_version`, `installed_sha256`, `stale`, `reloadable`, `refusal`); `gm-mcp http-status` prints it. A dispatch reply that is not file content or a paged spill file carries one line naming both versions, once per installed bundle (`bundleStalenessNotice`; a new installed sha re-arms it). `fs_read`, `result` and `gm_result` are excluded.

## Child reaper and attribution

- **Attribution gates reaping.** `child-ledger.js` rows name the dispatch that spawned each pid. Only attributed exec children are candidates (`DEFAULT_LEAK_KINDS = ['exec']`); the spool runner, http server and supervisor are detached on purpose. A stdio server is spawned by its MCP client and has no ledger row: `liveMcpClientInParentChain` judges it from the host process table, and an unreadable ancestor is unmeasured (null), never no-client.
- **Verdict.** `verdictOf` answers `unknown` if any predicate is unmeasured (null), `keep` if any fails, and `retire` only when all pass.
- **Parent and browser predicates.** `parentAbandoned`: a dead parent is abandoned; on win32 a live parent never is; on POSIX pid 1 or 2 counts. A browser whose command line has `--user-data-dir` belongs to a lane; without it, it is the user's own and protected.
- **Unmeasured is not absent.** `portListenerState` (`ports.js`) answers `measured: false` for an invalid port and `hasListener: null` when unmeasured; only a measured answer licenses retiring a port.
- **Leak watch.** `src/leak-watch.js` runs on the hourly pass of the scheduler in `src/self-update.js` (`scheduleStaleDeployedBundleChecks(onRefreshed, hourlyPass)`). It reads the host process table once and shares that table across the census, the reaper, the orphan scan and the supervisor duplicate count. A notable pass writes a `leak-watch` diagnostic and one stderr line; a clean one writes nothing. `gm-mcp-server.js leak-watch [--apply] [--json]` runs the same pass by hand. Env: `GM_MCP_LEAK_WATCH=0` disables the pass, `GM_MCP_LEAK_POPULATION_WARN=<n>` moves the population warning threshold (default 8), `GM_MCP_LEAK_AUTO_APPLY=1` arms auto-retire.
- **Auto-retire is narrower than the reaper's verdict.** It applies to `unattributed-server` findings of transport `stdio` only. `autoApplyDecision` adds guards: not the pid answering `/health` or owning a registered port, no live MCP-client or live-session ancestor, a measured start time at least `DEFAULT_MIN_RETIRE_AGE_MS` (30 min) old, and at most `DEFAULT_MAX_AUTO_RETIRE_PER_PASS` (3) per pass. A process whose ancestry or age cannot be measured is never signalled. `liveSessionNameOf` (`src/process-table.js`) names desktop and session managers that look like multi-day orphans (`selkies`, `xfdesktop`, `xfce4-session`, `s6-svscan`, `Xvfb`, ...); a candidate with such an ancestor is exempt.
- **Orphans.** `src/orphan-scan.js` rides the same pass and table read. A candidate is a pid whose `ppid` is `1`, that no `child-ledger` row claims, that is heavyweight (`GM_MCP_LEAK_ORPHAN_RSS_MB`, default 150 MB) and idle (CPU seconds over seconds alive below `GM_MCP_LEAK_ORPHAN_DUTY`, default 0.02), after `GM_MCP_LEAK_ORPHAN_MIN_AGE_MS` (default 900000) alive. Eleven reparented runners took 3367 MB of a 7.8 GB box on 2026-10-15 at about 0.01 duty while the one live run kept burning CPU, so the duty ratio is the discriminator, not age. It reports `orphans` and never signals; there is deliberately no `GM_MCP_LEAK_ORPHAN_AUTO_APPLY`. `GM_MCP_LEAK_ORPHANS=0` disables it. Each orphan root gets a `trees` entry: its descendants, walked through `/proc/<pid>/stat` ppid, bounded at depth 16 and 512 members; `truncated` names the bound that cut a walk. The scan reads `/proc/<pid>/stat` and `/proc/<pid>/status`, never `ps`, since `ps` on a loaded box can exceed 120 s; mac and Windows have no `/proc`, so the section is empty there. The `comm` field may hold spaces and parens, so numeric fields are counted from the LAST `)`: index 0 after it is field 3, which puts utime at 11, stime at 12 and starttime at 19.
- **Population.** `populationOf` compares the gm-mcp process count against the threshold; RSS is not part of it. Duplicate `http-supervise --port <N>` supervisors are counted by `duplicateSupervisorFindings` and left to `retireDuplicateHttpSupervisors` (`GM_MCP_HTTP_SUPERVISOR_DUPE_REAP`). Counts match each row's own argv in the shared table, never a `pgrep -f` pattern, which matches the counting shell itself.

## Self-update and release channel

- **Any running copy keeps the deployed bundle current.** `src/self-update.js` refreshes the deployed `gm-mcp-server.mjs` under `GM_TOOLS_DIR`/`~/.gm-tools` from the release channel whichever copy runs the check; the result carries `self`, true only when the refreshing process is that file. `GM_MCP_SELF_UPDATE_DEPLOYED_ONLY` set to anything but `0`/`false`/`no`/`off` restores the rule that only the deployed copy's own process refreshes it (`not-deployed-copy`); a missing deployed copy is reported as `no-deployed-copy` and never created. `refreshStaleDeployedBundleInBackground` calls `onRefreshed` only when `result.self === true`, since a repo-build process must not hand its listen handle to bytes it is not running. `bin/gm-mcp-server.js` on `main` is the live release channel: a pushed drifted bundle reaches every deployed copy within an hour.
- **A bare swap silently undoes a lost fix.** The 2026-10-04 build lost `windowsHide: true` on 1 of 3 child-spawn sites. Three guards gate `replaceDeployedBundle`, mirroring the runner's:
  - Freeze: `GM_MCP_NO_SELF_UPDATE` set to anything but `0`/`false`/`no`/`off`, or `gm-mcp-server.no-self-update` in `$AGENTPLUG_HOME` (else `~/.agentplug`), checked before the fetch.
  - Local-build pin: `gm-mcp-server.local-build.json` (sha256, path, version, ts), refused while the installed sha256 matches; written and cleared by `pin-local-build`/`unpin-local-build` in `src/cli.js`.
  - No downgrade: `BUNDLE_VERSION` (`src/bundle-version.js`) is compared numerically per component, so 0.10.0 beats 0.9.0.
  Each refusal returns `outcome: 'refused'` with a `code` and logs one stderr line. Bumping `BUNDLE_VERSION` is part of every deploy. The version is read from the candidate's bytes, so keep the `BUNDLE_VERSION = "x.y.z"` assignment recognizable to `BUNDLE_VERSION_ASSIGNMENT`. `scripts/build.mjs` derives that banner from the source version, and `verify-build` checks the updater parser against it. CI checks out with `fetch-depth: 0` so `scripts/check-version-bump.mjs` sees the pushed range.
- **Release channel cadence.** The freshness probe is `api.github.com/repos/AnEntrypoint/gm-mcp/commits/main` with `If-None-Match` on the stored API ETag, so an unchanged head costs headers only; a changed head sha is fetched from its commit-addressed raw URL. The 10-minute unconditional raw-main fetch runs only when the probe fails. A fix pushed upstream reaches the machine within one interval (`GM_MCP_SELF_UPDATE_INTERVAL_MS`, default 60 s). `self-update-now` (`src/cli.js`) runs `refreshDeployedBundleNow`: the same refresh with `ignoreStamp`, so the stamp-freshness deferral is the only thing it skips. Freeze, local-build pin, no-downgrade, `same-build`, the shebang, size and `node --check` gates and the inflight-dispatch wait all still hold. It arms no retry timer and calls no `onRefreshed`, so a one-shot run beside a server holding 8787 starts nothing. It records `self-update-check` with `forced: true` and prints the previous and new versions plus `describeSelfUpdateOutcome(result)`.
- **Out-of-band controls.** Four operator-set controls gate self-update: the freeze, `GM_MCP_SELF_UPDATE=0`, `GM_MCP_SELF_UPDATE_DEPLOYED_ONLY`, and the local-build pin. The release channel cannot write them. The fetch URL (`GM_MCP_BUNDLE_URL`, else `DEFAULT_BUNDLE_URL` on raw `main`) is the publisher's own, so a publisher-side compromise passes every guard except the operator-set ones.
- **Release bridge (`src/release-bridge.js`).** Runs on every stdio connect and HTTP start, at most once per 10 minutes (state in `gm-mcp-release-bridge.json` under `AGENTPLUG_HOME`; `GM_MCP_RELEASE_BRIDGE_INTERVAL_MS` overrides, `GM_MCP_RELEASE_BRIDGE=0` disables). It upgrades the installed `agentplug-runner` and `gm.wasm` from the latest `AnEntrypoint/agentplug-bin` and `plugkit-bin` releases. Integrity is the published `.sha256` sidecar alone: it proves the bytes match the sidecar, not who published them. The runner is taken only when `--build-info` reports a release build at exactly the tag's version; `gm.version` is written as bare semver. Each swap renames the installed file to a `.bak-<from>-<stamp>` sibling and deletes none. The freeze env vars, the freeze files (`gm-mcp-server.no-self-update`, `agentplug-runner.no-self-update`) and a runner local-build pin are honored. A non-semver `gm.version`, a `gm.local-dev-sideload.json` marker, or a `gm.build.json` whose `origin` is not `"release"` marks a sideload and is never overwritten. After a swap it sends SIGTERM to the daemon in `daemon-status.json` when its owner lock, where present, names the same pid (on Linux the pid must be an `agentplug-runner` image) and it does not already report the new sha; a dispatch in flight defers the signal into the state file.
- **Release records.** `recordRunnerSwap` writes `agentplug-runner.version` and `last-completed-runner-swap.json`; the daemon's parity reader is outside this repo, so that parity is unverified here. `recordGuestBuild` writes `plugins/gm.build.json` with `source_sha` from the release body's `source-head:` line. Release assets are accepted only from `https://github.com/<repo>/releases/download/`.
- **Self-update decision record (ADR-GMMCP-SELFUPDATE-1).** Accepted. `src/self-update.js` `versionGuardReason(candidateBytes, installedBytes)` refuses a candidate older than the installed version (`no-downgrade`) and a byte-identical candidate (`same-build`); an equal-version candidate with different bytes is eligible. The guard compares build identity, not the version string alone, as the root `AGENTS.md` Implementation rules require. The windowsHide regression is not a version question, so the freeze and the local-build pin remain its controls.

- **Push gate and bundle ownership.** While `.github/workflows/bundle.yml` exists, a push that changes `src/` without `bin/gm-mcp-server.js` passes `scripts/check-bin-drift.mjs` (the runner's push gate runs it from the pushed commit) and `scripts/check-version-bump.mjs`: CI rebuilds the bundle on main after the push with `[skip ci]`. esbuild is not needed locally. Without it the drift check compares only the bundle's recorded `BUNDLE_SRC_SHA256` against `src/`; the byte-for-byte comparison runs in CI, where `npm ci` installs esbuild.

## Bundle drift and handover

- **A process runs its launch bytes.** Node reads the bundle once, so a newer bundle installed over `~/.gm-tools/gm-mcp-server.mjs` reaches a long-lived server only through a reload. Two triggers: `refreshStaleDeployedBundle` (release channel, every minute, conditional fetch, file against URL) and `startBundleDriftWatch` (`src/bundle-drift.js`, every 30 s, file against this process's bytes). The release-channel check answers `current` whenever file and URL agree, so alone it never picks up a hand-installed bundle.
- **Drift measurement.** The running side is `launchedEntryPath()`; the installed side is `serverEntryPath()`, and the notice names that installed path (cached by size and mtime). `bundleDrift()` answers `stale` on a hash difference and `reloadable` only for a single-file bundle whose `BUNDLE_VERSION` is not older than the running one. `no-downgrade`, `installed-version-unknown` and `running-not-a-bundle` (a dev checkout would restart on every edit) report staleness and refuse the reload. `GM_MCP_BUNDLE_DRIFT_RELOAD=0` disables reloads and keeps the reporting.
- **Stdio reloads by relaying, not exiting.** Exiting would detach the client, because its `StdioClientTransport` closes on this child's `close` event. `handOverStdioToRefreshedBundle` (`src/bundle-refresh.js`) spawns the installed bundle as a child on its own pipes, then in one synchronous step drops the SDK transport's `data` listener from `process.stdin` and pipes stdin to the child and the child's stdout to `process.stdout`, so exactly one reader owns the frames. MCP stdio frames are newline-delimited JSON, so the relay copies bytes and parses nothing. The child is adopted only once its stderr carries `connected, serving on stdio`.
- **HTTP reloads hand over the socket.** `handOverToRefreshedBundle` (`src/bundle-refresh.js`) spawns the new bundle with an IPC channel, sends the listening `net.Server`, and stops accepting only once the child answers `gm-mcp-handover-ready`. The child adopts it with `server.listen({ handle })` from the raw `_handle`. Close-then-bind is the fallback when the ready reply never comes, and `takePortBack` re-listens if the replacement never answers `/health`.
- **Reloads never cut work.** Nothing starts while `inflightDispatchCount() > 0` (`bundle-handover-deferred`, retried next tick), and the outgoing process waits for that count to reach 0 before `process.exit(0)`. `drainAndExit` applies the same wait to open connections; the stdio relay detaches the SDK listeners by identity and pauses stdin.

## Verbs, witnesses and probes

- **Verb list.** The verb set is one table in `src/verb-table.js`. `RUNNER_REGISTRY_VERBS` (`src/verbs.js`) derives from it, and `runnerVerb(row)` is the only place the runner's hyphen spelling is produced. Each entry is a `gm.<verb>` binding inside the single MCP tool `gm_codemode` (`src/codemode.js`), named by `verbToolName`. A verb missing from the list has no binding.
- **Witness and probe scripts.** `scripts/pool-observe-served-witness.mjs` checks the served pool-observe output against the candidate contract in `../rs-plugkit/crates/plugkit-core/src/orchestrator/pool_rank.rs`. `test/mcp-http-probe.mjs` is a manual probe outside `npm test`.
