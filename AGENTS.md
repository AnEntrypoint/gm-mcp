# AGENTS.md

Repo-source facts that structure and naming cannot carry. The exec-family `timeoutMs` prefix and the `raw_body`/plain-text contract are in README.md ("Exec-family timeout prefix").

## Runner and daemon liveness

- **Runner recovery.** The daemon exits on purpose and this process brings it back. It self-recycles when idle (`self-recycling after 3600000ms fully idle` in `~/.agentplug/daemon.log`) or over its wasm memory ceiling, and hands off to a freshly downloaded runner build; a cold start costs tens of seconds of wasm compile. `ensureSpoolRunnerRunning` recovers any dead daemon, so recovery speed depends on how fast this process notices death. Judge liveness by `status.json`'s `pid` via `process.kill(pid, 0)` (`liveDaemonSweepsProject`), never by heartbeat age: the old `SWEEPER_HEARTBEAT_TRUSTED_MS` (120 s) window let a dead daemon sit undetected. `daemonBootGraceActive` covers a fresh `daemon_boot_ts` in `~/.agentplug/daemon-status.json` that has not swept any project yet. The ensure spawn is idempotent (a runner started against a live daemon only registers the project and exits), so keep `ENSURE_INTERVAL_MS` (2 s) and `ENSURE_LEASE_MS` (3 s) small; large values recreate the dead window in which dispatches sit `queued_not_yet_claimed`. `startRunnerWatchdog` re-checks every root every 5 s (opt out `GM_MCP_RUNNER_WATCHDOG=0`); recovery used to wait for the next dispatch. No `status.json` means never swept: that is registration, not a liveness verdict.
- **Dead-daemon pre-flight.** A ticket written into a dead spool waits unclaimed, and the spool cannot say "nobody is listening", so `daemonNotRunning` runs before `publishSpoolRequest`. A stale heartbeat gets one `ensureSpoolRunnerRunning` plus `DAEMON_START_GRACE_MS` (15 s); only then does the call return `error: daemon-not-running`, unwritten. It does not fire with no `status.json`, inside `daemonBootGraceActive`, or during `runner_update_in_progress`, where a stale heartbeat is expected and the dispatch must go through. The grace is bounded and reported, not 120 s of silence. `GM_MCP_DAEMON_PREFLIGHT=0` bypasses it.

## Dispatch wire and polling

- **Glob filters are validated here and forwarded untouched.** `codesearch` and `grep` read `glob`, `path_glob`, `include`, `exclude_glob` and `exclude_globs` as a string or array of strings; the wasm matches them (`!` excludes, `{a,b}` brace lists work, aliases merge). `withGlobFiltersCoerced` only trims entries and fails loudly on what the wasm would silently ignore: a non-string/non-array value, an empty string, an empty array or a blank entry. Never join an array into one brace glob: that rewrote entries containing `,`/`{`/`}` and refused `!`. The wasm echoes `path_glob` and `files_matching_glob`, and sets `glob_matched_no_files: true` when nothing matches.
- **Waited dispatches disclose it.** A reply landing after `DISPATCH_WAIT_DISCLOSED_AT_MS` (5 s) carries `dispatch_waited_ms`, so queue time shows on success too. `codesearch` `timeout_ms` is a scan wall-clock budget (regex default 20000) enforced in the wasm; its overrun reply is `timed_out: true`, `exhaustive: false`, `budget_ms`.
- **Timeout prefix sync.** `TIMEOUT_MS_PREFIX_LINE` mirrors the rs-plugkit `strip_timeout_ms_prefix_directive`: skip leading whitespace; the first line must start with `timeoutMs=` or `timeout_ms=`. Keep the two in sync.
- **Instruction hash assertion.** `deliveredInstructionHashByOwner` caches, per (project root, `session_id`), the hash of the `instruction` prose last returned to that caller. `withAssertedInstructionHash` asserts it on the next `instruction` dispatch so gm can answer `instruction_unchanged: true` instead of resending tens of kilobytes. The cache is process-lifetime and keyed on session as well as root: a restarted server must resend the prose rather than inherit an assertion it cannot honor.
- **Poll budgets.** `pollTimeoutMs` computes the requested budget, not what the daemon enforces. An explicit `timeout_seconds` wins. Otherwise an exec body starting with `timeoutMs=<ms>` requests that plus 5 s (never under 120 s), because the daemon kills the child tree at its wall-clock `timeoutMs` and answers `exec_timeout`. A wrapper-injected prefix follows the poll budget minus 5 s, floored at 300 s (`EXEC_DEFAULT_LIMIT_SECONDS`) and capped at 900000 ms (`EXEC_HARD_CEILING_MS` here; agentplug-host's `HARD_CEILING_MS`), so a 400 s caller is not told "in flight" for work reaped at 300 s. A poll without a prefix waits 120 s. A `resume_task` poll sends no body, so it has only `timeout_seconds`. Every initial or resume poll is capped at 600 s (the harness tool-call maximum; `GM_MCP_POLL_TIMEOUT_CEILING_MS` overrides). A poll timeout reports requested and applied budgets, the ceiling and why it ended; it neither cancels nor republishes execution, and it names the exec child's `timeoutMs` deadline.
- **Exec output envelope.** `unpackExecOutputEnvelope` parses the `data` JSON string before cleaning, so `stdout`, `stderr` and `result` keep their own 16000-char cap (`EXEC_OUTPUT_FIELD_TRUNCATE_AT`) instead of the 400-char cap of the packed string. The marker names `result_file` (set when a field exceeds 2000 chars) or, for an older daemon, the out-file. A structured `result` is capped by compact JSON length only when `result_file` is present.

- **Hand-written JSON.** `normalizedObjectBody` (`dispatch.js`) passes a non-object string through as raw text; an escape-looking parse error gets a repair hint naming the escape.
- **Spool reads.** Symlinks are refused before open; the opened file is checked by dev and ino, never by a `/proc` or `/dev/fd` path (`dispatch.js`).
- **Alias fields are per handler.** `git_reset` reads `ref|rev` and `mode|hard`; `git_revert` reads `ref` alone, so a `rev` alias would be silently ignored (`verb-table.js`).

## Response compaction

- **Two stages.** In `src/response-compact.js`, `cleanResponse` is lossless housekeeping: it strips opaque ids, drops empties except the answer lists in `EMPTY_LIST_IS_THE_ANSWER_KEYS` (an empty `candidates` prints `[]`), and truncates prose with a pointer at `LONG_TEXT_FIELD_TRUNCATE_AT` (400 chars). A plain-text-body verb (`isPlainText` in `dispatch.js`) gets `PLAIN_TEXT_OUTPUT_INLINE_MAX` (32768, read once from env at start), because its whole response is the script's output; raising the generic cap instead would un-truncate `instruction`'s prose, which the wire measurements are tuned against. `fs_read` gets `FILE_READ_INLINE_MAX` (65536): at 400 chars every whole-file read became a pointer and callers fell back to host reads. `max_chars` overrides the defaults.
- **Full response.** `full_response: true` bypasses cleaning, data flattening, native-envelope decoding and wire compaction, so every guest field and layout survives; the response file stays bounded by the 4 MiB read limit. Exec-family fields keep `EXEC_OUTPUT_FIELD_TRUNCATE_AT` and `result_file`. Default responses keep actionable `dispatch_id` evidence; `request_fingerprint` is omitted by default and kept in full responses.
- **Failures are not compacted.** Compaction runs only when the response has no failure. Faults keep their diagnostics, except that default responses omit `stdout` when it is a nonempty JSON object deeply equal, field for field, to the containing fault object; the response names the original spool file.
- **Field decisions.** Dropped: `route_hint`, `reply_hash`, `orient_nouns` (routing telemetry); `supply_chain_scan` when it has no findings (with findings it stays whole, `warnings` capped at 8 with `warningsOmitted` beside `warnCount`); `session_owner_before_this_dispatch` unless `session_mismatch` is true. Collapsed to counts: `codeinsight_overview` (`by_kind`, `by_language`, `largest_files`), `codeinsight_start` (to `{ready: true}`, whole when not ready, since that is when it is actionable), `config_changed` (newest transition, 3 keys), `dream_rsi_strategy`, `dream_rsi_replay`. Row and hit prose in `ready_wave`, `prd_items`, `mutables_pending`, `recall_hits`, `bm25_hits` and `vector_hits` is excerpted, with `id`/`key`/`status`/`session_id`/`verb` exempt so a row stays addressable; `recall_hits` caps at the top 4. Kept whole: `instruction`, `phase`, `ok`, `session_id`, `instruction_hash` and `policy_hash` (assert-protocol inputs the caller resends), `discipline_policies` (emitted only when the policy hash moved, so it is the thing to read), and every count.
- **Count mode.** Wire compaction of count results requires explicit `ok: true`, `exhaustive: true`, no failure or partial diagnostics, and same-length exact `path:count` parity between `output` and structured `counts`. Only the derived `output` is omitted; count rows, totals and scan metadata stay whole.
- **Phase history and receipts.** `phase_history` is context, not the current phase or a gate decision: the wire keeps its newest five transitions in source order with retained/total counts. Current phase, session mismatch and pending-work counts stay authoritative and unshortened. Committed `git_commit`/`git_finalize` successes keep at most five received `excluded` and `excluded_but_dirty` examples; the metadata counts received examples, not native totals. Count and truncation fields, requested paths, SHA and authors stay whole. Failures, refusals and uncommitted receipts bypass this, as does `full_response: true`, which (with the full-payload pointer) recovers the received arrays, not examples absent from the native receipt.
- **Measured** (`scripts/measure-wire-size.mjs`, real `instruction` out-files): 7839->3737, 8766->5306, 9507->4959 bytes; live session 8815->5355.

- **Zero hits.** A search reply with no hits is annotated `zero_hits_is_not_a_finding` unless the scan covered its files (`searched_zero_files`): "0 hits" and "code absent" are identical bytes.

## Working directory, sessions and dev sync

- **Cold projects are not a git-root problem.** A non-git cwd is rooted on itself (`projectRootFor`) and the daemon registers and sweeps it like any project. Measured 2026-10-05: first claim took 85-110 s on cold projects (shared daemon, 100+ projects; `queue_wait_ms` 40-90 s). Non-git cwds need no `git_root_override`; the timed-out note says so and points at `resume_task`.
- **Plain-text ownership.** Plain-text replies carry a byte-zero `gm_session_id=<owner>\n` header before the timeout directive; the guest advertises `gm_session_header_version: 1`. MCP probes with a safe JSON `phase-status` and caches only a coherent result bound to project, daemon boot, PID and GM hash; every nonempty pool slot must agree, and a new hash or mixed pool invalidates it. Legacy or unverified guests get the original text with `owner_transport: legacy-unverified` or `unverified`; nothing is retried.
- **In-flight count.** `inflightDispatchCount()` feeds the exit and signal records, the self-update check (`deferred-dispatch-inflight`) and the runner-swap signal (`dispatch-in-flight`). A bundle swap waits for dispatches too, because a failure during a dispatch looks like a network stall. A process quitting mid-dispatch strands the spool ticket it wrote, and nothing polls for its reply.
- **Cwd-less dispatch never guesses.** The root comes from the `cwd` argument, then `GM_MCP_DEFAULT_CWD` or `CLAUDE_PROJECT_DIR`, then the server cwd only when it is a git toplevel (or `GM_MCP_ALLOW_PROCESS_CWD=1`); otherwise the reply is `error: cwd-required`. A shared server launched from $HOME once wrote state into $HOME/.gm while the caller's spool stayed empty.
- **Leases.** `ensureAgentLease` attaches a project by writing `<agentplugDir()>/leases/<key>.<pid>.lease` with the project root, once per project and pid. The daemon-side rule (it watches a project only while a lease exists) is not verifiable here.
- **Layout cache.** `git-adapter.js` caches only `rev-parse` layout questions (`LAYOUT_QUESTION_FLAGS`); gating reads such as `status --porcelain` are never cached.
- **Dev sync.** `runDevSync` syncs the parent before its submodules, because the parent's `--ff-only` merge moves submodule pins; a submodule fast-forwards only when on `main`. `maybeStartDevSync` never blocks a dispatch: the child is detached and unref'd, stamps are written before the spawn, and one sync starts per 10 minutes (`SYNC_INTERVAL_MS`) across all roots. Stamp keys are absolute roots plus `*` (the global throttle); no absolute path equals `*`.

## Process resilience and diagnostics

- **Stdio never exits on errors.** `keepServingOnAsyncFailure` (uncaught, unhandled, stdin and stderr errors) and `surviveClientGone` (stdout EPIPE, stdin end) record and continue. A dispatch is a spool ticket someone waits on; exiting would turn a recoverable stall into a dead session. Each stdout error code is recorded once.
- **Signal and exit records.** `logSignalExits` records SIGINT, SIGTERM, SIGHUP and SIGBREAK, then exits 0, so the exit status hides the signal; the `exit` record carries it. That record in `src/transport-guard.js` also carries `uptime_ms`, which survives the repeat filter (it ignores `pid`), so two servers exiting with the same code in one window each leave a line. A killed singleton leaves no `exit` record, because `logSignalExits` only sees signals a handler runs for.
- **Stdout guard.** `isJsonRpcFrame` checks that the first byte is `{` before parsing, since every stdout write passes through it and a response can be about 1 MB. Anything else is diverted to stderr as `stdout-write-diverted`.
- **Diagnostics.** `appendDiagnostic` writes each record to stderr and, unless repeat suppression holds it, to `logFilePath()` (`gm-mcp-server.log`, rotated to one `.1` past 2 MB by `src/server-log.js`). An identical event and fields within 60 s are counted, not written (ignoring `ms`, `inflight`, `dispatches_inflight` and `pid`); the next write of that key is preceded by `repeat-suppressed`. The host discards stderr, so the file is the durable record.
- **Runtime-only logs.** `gm-mcp-server.log` and `dev-sync.log` (`src/dev-sync.js` `logPath()`, one JSON line per sync run, under `agentplugDir()`) live outside the repository. No module or verb reads either back, so they are output, not state; deleting them changes no dispatch.

## HTTP transport and singleton

- **Singleton is opt-out.** One shared server per machine, keyed by port. `httpSingletonEnabled` (`src/singleton.js`) is off only when `GM_MCP_NO_HTTP_SINGLETON` or `GM_MCP_HTTP_SINGLETON_OFF` is set to anything but `0`/`false`/`no`/`off`, or the legacy `GM_MCP_HTTP_SINGLETON=0`. An agent host registered with the HTTP url never launches this server, so with nothing listening its connection fails for the whole session and every gm tool is absent. Hence the default is on, a stdio session seeds one in the background (`seedHttpSingletonInBackground`, `src/index.js`), and `gm-mcp dispatch` seeds one awaited with `wait: false` (`src/cli.js`), since dispatch runs with no MCP client and doubles as the revival path. `ensureHttpSingleton` trusts the health probe on the port over the state file (`gm-mcp-http.json`), which is only a hint. The spawned singleton runs the bundle this process launched from (`launchedEntryPath`), not whichever `gm-mcp` resolves first, and inherits `GM_MCP_HTTP_SINGLETON=0`: seeding inside the singleton would spawn a server on the port it already holds.
- **Supervisor.** `ensureHttpSupervisor` (`src/singleton.js`) spawns one detached, unref'd sibling per port that probes `/health` on a timer and reruns the start path when answers stop, so a dead server returns with no session, cron job or human, even one killed too hard to write an `exit` line. Detached, because a caller-parented supervisor dies with the caller's tree. Opt-out: `GM_MCP_HTTP_SUPERVISOR=0`, for the same reason as the singleton. An HTTP-transport process arms it (it alone knows the port should be up), and `ensure-http` arms it on every run. The child inherits `GM_MCP_HTTP_SUPERVISOR=0`, or every server it restarts would arm a second supervisor. `runHttpSupervisor` runs in the foreground so a service manager can hold it. Two supervisors on one port are harmless: revival goes through `ensureHttpSingleton`, which probes before spawning. Liveness is the state file's `ts`, refreshed each pass and stale after `SUPERVISOR_STATE_STALE_MS` (60 s), not its pid: a recycled pid would leave the port unwatched for good.
- **Instance registry.** Each HTTP-transport process registers in `<agentplugDir()>/gm-mcp-http-instance-<port>.json` (`recordHttpInstance`): pid, bundle version, entry path and the supervisor pid it armed. The port is the instance key, so a second `GM_MCP_HTTP_PORT`/`--port` is a legitimate second instance. `registeredHttpPorts()` enumerates instance files, supervisor files and `gm-mcp-http.json`. `sweepHttpInstances()` runs in `ensure-http` and on every supervisor pass:
  - `reapDeadHttpInstances` drops all three files of a port whose server is gone, so the number is reusable rather than walking to a fresh port.
  - `replaceBehindHttpInstances` retires a server whose `/health` version is behind this process's `BUNDLE_VERSION` (`versionBehind`) and starts a fresh one on the same port, so an attached session reconnects to current code rather than losing the port.
  - `reapOrphanedHttpInstances` stops one with no live supervisor, a provably dead parent (`parentPidOf`) and zero established connections (`establishedConnectionCount`). A null answer (the platform cannot say) and any nonzero count are never reaped.
  A version replacement also stops that port's supervisor, or the old one would respawn the old bundle, and re-arms it with `ensureHttpSupervisor({force:true})`, since a supervisor carries `GM_MCP_HTTP_SUPERVISOR=0` in its env and would otherwise answer `disabled`. `ensureHttpSingleton` applies the same version test to its port and retires a recorded pid that holds the port but answers no health check.
- **Stateless transport.** No session id is issued; every POST builds a fresh server and transport (`serveStatelessMcpRequest`), because the SDK throws "Stateless transport cannot be reused across requests" on a second request through one transport. Non-POST requests to `/mcp` get 405. `startHttpServer` records `http-listen-failed` with the errno `code` before rethrowing, since the only handler above it prints to stderr, which the host discards.
- **Protocol version.** After `initialize`, the SDK answers 400 to an `mcp-protocol-version` outside `SUPPORTED_PROTOCOL_VERSIONS` (SDK 1.30.0, `validateProtocolVersion`). `normalizeProtocolVersion` rewrites the header to `SUPPORTED_PROTOCOL_VERSIONS[0]` (the newest, 2025-11-25) before the SDK reads it; without that, a current client's calls get 400 and the server looks dead.
- **Supervision outside this repo.** The singleton on 8787 is detached and unref'd, so nothing in this tree restarts it. Once it dies the port stays dead until something seeds one, and a client that POSTs straight to the port (a shell bridge such as `gmc.py`) gets `ECONNREFUSED` with nothing to seed a replacement; this is not OOM and not a crash. `scripts/install-autostart.mjs` fixes it: it writes a managed block into `$HOME/beforestart` (boot) and `$HOME/crontab` (`@reboot` plus a minutely `ensure-http` guard), runs `ensure-http` once, probes `/health` first, and is idempotent so it never starts a second server. Reinstall: `node scripts/install-autostart.mjs`; uninstall: `--uninstall`; dry run: `--check`. Manual revive and status: `node ~/.gm-tools/gm-mcp-server.mjs ensure-http` / `http-status`. Guard log: `$HOME/logs/gm-mcp-autostart.log`; server log: `gm-mcp-server.log`.

- **Body cap and listen retry.** `readCappedJsonBody` counts bytes as they arrive (Content-Length alone lets chunked bodies through). `EADDRINUSE` is retried until the listen deadline, with or without an adopted handle (`http-transport.js`).

## Child reaper and attribution

- **Attribution gates reaping.** `child-ledger.js` rows name the dispatch that spawned each pid. Only attributed exec children are candidates (`DEFAULT_LEAK_KINDS = ['exec']`); spool runner, http server and supervisor are detached on purpose.
- **Verdict.** `verdictOf` answers `unknown` if any predicate is unmeasured (null), `keep` if any fails, and `retire` only when all pass.
- **Parent and browser predicates.** `parentAbandoned`: a dead parent is abandoned; on win32 a live parent never is; on POSIX pid 1 or 2 counts. A browser whose command line has `--user-data-dir` belongs to a lane; without it, it is the user's own and protected.
- **Unmeasured is not absent.** `portListenerState` (`ports.js`) answers `measured: false` for an invalid port and `hasListener: null` when unmeasured; only a measured answer licenses retiring a port.

## Self-update and release channel

- **Deployed bundle only.** `src/self-update.js` replaces only the file it runs from, and only when that is the deployed `gm-mcp-server.mjs` under `GM_TOOLS_DIR`/`~/.gm-tools`. A dev checkout or `src/` run reports `not-deployed-copy` and is never overwritten. The fetch runs after `server.connect`, so the 30 s connect window is never delayed, and the new bundle serves from the next connect unless the transport hands over in-process (see "Bundle drift and handover" below). Therefore `bin/gm-mcp-server.js` on `main` is the live release channel: a pushed drifted bundle reaches every deployed copy within an hour.
- **A bare swap silently undoes a lost fix.** The 2026-10-04 build lost `windowsHide: true` on 1 of 3 child-spawn sites. Three guards gate `replaceDeployedBundle`, mirroring the runner's:
  - Freeze: `GM_MCP_NO_SELF_UPDATE` set to anything but `0`/`false`/`no`/`off`, or `gm-mcp-server.no-self-update` in `$AGENTPLUG_HOME` (else `~/.agentplug`), checked before the fetch.
  - Local-build pin: `gm-mcp-server.local-build.json` (sha256, path, version, ts), refused while the installed sha256 matches; written and cleared by the `pin-local-build`/`unpin-local-build` subcommands in `src/cli.js`.
  - No downgrade: `BUNDLE_VERSION` (`src/bundle-version.js`) is compared numerically per component, so 0.10.0 beats 0.9.0.
  Each refusal returns `outcome: 'refused'` with a `code` and logs one stderr line naming the reason, since the check runs in the background where a silent refusal looks like a quiet channel. Bumping `BUNDLE_VERSION` is part of every deploy: a release that keeps the installed version is refused everywhere. The version is read from the candidate's bytes, so keep the `BUNDLE_VERSION = "x.y.z"` assignment recognizable to `BUNDLE_VERSION_ASSIGNMENT`. `scripts/build.mjs` derives that banner from the source version, and `verify-build` checks the updater parser against it before checking byte drift.
- **Out-of-band controls.** The bundle self-update has three operator-set off controls: the freeze (`GM_MCP_NO_SELF_UPDATE` or `gm-mcp-server.no-self-update`), the `GM_MCP_SELF_UPDATE=0` switch (`refreshStaleDeployedBundle`), and the local-build pin. The release channel cannot write any of them. Every other guard reads the candidate's own bytes (shebang, `node --check`, `parseBundleVersion`) or the deployed file's hash. No bundle digest comes from a channel the publisher does not write: the fetch URL (`GM_MCP_BUNDLE_URL`, else `DEFAULT_BUNDLE_URL` on raw `main`) is the publisher's own, so a publisher-side compromise passes every guard except the operator-set ones.
- **Release bridge (`src/release-bridge.js`).** Runs on every stdio connect and HTTP start, at most once per interval (10 minutes; state in `gm-mcp-release-bridge.json` under `AGENTPLUG_HOME`; `GM_MCP_RELEASE_BRIDGE_INTERVAL_MS` overrides, `GM_MCP_RELEASE_BRIDGE=0` disables). It upgrades the installed `agentplug-runner` and `gm.wasm` from the latest `AnEntrypoint/agentplug-bin` and `plugkit-bin` releases. Integrity is the published `.sha256` sidecar alone: it proves the bytes match what was published, not who published them. The runner is taken only when `--build-info` reports a release build at exactly the tag's version; `gm.version` is written as bare semver. Each swap renames the installed file to a `.bak-<from>-<stamp>` sibling and never deletes one. A freeze (`GM_MCP_NO_SELF_UPDATE`, `AGENTPLUG_NO_SELF_UPDATE`, or either freeze file, `gm-mcp-server.no-self-update` or `agentplug-runner.no-self-update`) and a runner local-build pin are honored. A non-semver `gm.version`, a `gm.local-dev-sideload.json` marker, or a `gm.build.json` whose `origin` is not `"release"` marks a sideload and is never overwritten; the bridge and runner always write `"release"`, and a sideload script writes no origin. After a swap it sends SIGTERM to the daemon named in `daemon-status.json` under this `AGENTPLUG_HOME`, provided its owner lock agrees (on Linux the pid must be an `agentplug-runner` image) and it does not already report the new sha. A dispatch in flight defers the signal into the state file. The gm client's watchdog respawns the runner.
- **Release records.** `recordRunnerSwap` writes `agentplug-runner.version` and `last-completed-runner-swap.json` (version and sha256). The daemon's parity check reads them, but its reader is in neither this repo nor rs-plugkit, so that is unverified here. `recordGuestBuild` writes `plugins/gm.build.json` with `source_sha` from the release body's `source-head:` line. Release assets are accepted only from `https://github.com/<repo>/releases/download/`. When gm already matches the release, `reconcileGuestBuildRecord` still names that build in `gm.build.json`, so a build installed by another updater is recorded.

## Bundle drift and handover

- **A process runs its launch bytes.** Node reads the bundle once and nothing re-reads it, so a newer bundle installed over `~/.gm-tools/gm-mcp-server.mjs` (by a lane build, `dev-sync`, anything) reaches a long-lived server only through a reload. Two triggers exist: `refreshStaleDeployedBundle` (release channel, hourly, file against URL) and `startBundleDriftWatch` (`src/bundle-drift.js`, every 30 s, file against this process's bytes). The release-channel check answers `current` whenever file and URL agree, whatever this process runs, so alone it never picks up a hand-installed bundle; that gap is why the drift watch exists.
- **Drift measurement.** Drift is measured against `launchedEntryPath()` (cached by size and mtime, so the 1 MB hash runs only when the file moved). `bundleDrift()` answers `stale` on a hash difference and `reloadable` only for a single-file bundle whose `BUNDLE_VERSION` is not older than the running one. `no-downgrade`, `installed-version-unknown` and `running-not-a-bundle` (a dev checkout would restart on every edit) report staleness and refuse the reload. `GM_MCP_BUNDLE_DRIFT_RELOAD=0` disables reloads and keeps the reporting.
- **Stdio reloads by relaying, not exiting.** Exiting would detach the client, because its `StdioClientTransport` closes on this child's `close` event. `handOverStdioToRefreshedBundle` (`src/bundle-refresh.js`) spawns the installed bundle as a child on its own pipes, then in one synchronous step drops the SDK transport's `data` listener from `process.stdin` and pipes stdin to the child and the child's stdout to `process.stdout`, so exactly one reader owns the frames. MCP stdio frames are newline-delimited JSON, so the relay copies bytes and parses nothing. The child is adopted only once its stderr carries `connected, serving on stdio`; a dead child clears the relay and the next tick hands over again.
- **HTTP reloads hand over the socket.** `handOverToRefreshedBundle` (`src/bundle-refresh.js`) spawns the new bundle with an IPC channel, sends the listening `net.Server`, and stops accepting only once the child answers `gm-mcp-handover-ready`. The child adopts it with `server.listen({ handle })` from the raw `_handle`. Both processes hold the socket, so nothing goes unanswered during the switch (measured over 50 s of continuous probing across a handover: 42056 requests, 0 refused). Close-then-bind is the fallback when the ready reply never comes, and `takePortBack` re-listens if the replacement never answers `/health`.
- **Reloads never cut work.** Nothing starts while `inflightDispatchCount() > 0` (`bundle-handover-deferred`, retried next tick), and the outgoing process waits for that count to reach 0 before `process.exit(0)`, so a reply being written finishes.
- **Stdin drain.** The stdio relay detaches the SDK `data`/`error` listeners by identity and pauses stdin; with no bound handler it calls `transport.close()`. `drainAndExit` waits for the dispatch count and open connections to reach 0 before `process.exit(0)`.
- **Staleness is never silent, and is said once.** `/health` carries a `bundle` block (`running_version`, `running_sha256`, `installed_version`, `installed_sha256`, `stale`, `reloadable`, `refusal`); `gm-mcp http-status` prints it. A dispatch reply that is not file content or a paged spill file carries one line naming both versions, once per installed bundle rather than per reply: `bundleStalenessNotice` keys on running sha, installed sha and refusal code and returns null after the first line; a new installed sha re-arms it. `fs_read`, `result` and `gm_result` are excluded because their replies are handed back byte for byte, and an appended line would change the file.

## Architecture decisions

### ADR-GMMCP-SELFUPDATE-1: the self-update guard compares build identity

- **Status.** Accepted by the user (session gm-backlog-w2-05, option a). Implementation is pending: `src/self-update.js` still applies the version comparison in the "No downgrade" bullet above until the implementing row lands.
- **Context.** `scripts/check-version-bump.mjs` requires a `BUNDLE_VERSION` bump on every `src/` change, and the no-downgrade test is strictly forward on that string. A candidate built at an equal version is therefore refused, even when its bytes differ.
- **Decision.** The guard compares build identity, the candidate's build stamp and bytes against the installed bundle, and not the version string alone. A same-version candidate with a different build identity is eligible. This is the repo rule for self-update guards (root `AGENTS.md`, Implementation rules).
- **Consequences.** An equal-version release stops being refused by the version test. The build stamp field is chosen by the implementing row, not here. The windowsHide regression (see "A bare swap silently undoes a lost fix") is not a version question: the build-identity guard alone would accept a swap that drops a fix, so the freeze and the local-build pin remain the controls against it.
