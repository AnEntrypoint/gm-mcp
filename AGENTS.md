# AGENTS.md

Repo-source facts that structure and naming cannot carry. The exec-family `timeoutMs` prefix and the `raw_body`/plain-text contract are in README.md ("Exec-family timeout prefix").

## Runner and daemon liveness

- **Runner recovery.** The daemon exits on purpose and this process brings it back. It self-recycles when idle (`self-recycling after 3600000ms fully idle` in `~/.agentplug/daemon.log`) or over its wasm memory ceiling, then hands off to a freshly downloaded runner build; a cold start costs tens of seconds of wasm compile. `ensureSpoolRunnerRunning` recovers a dead daemon. Liveness is judged by `status.json`'s `pid` via `process.kill(pid, 0)` (`liveDaemonSweepsProject`), never by heartbeat age, which let a dead daemon sit undetected. `daemonBootGraceActive` covers a fresh `daemon_boot_ts` in `~/.agentplug/daemon-status.json` that has not swept any project yet. The ensure spawn is idempotent, so `ENSURE_INTERVAL_MS` (2 s) and `ENSURE_LEASE_MS` (3 s) stay small; large values recreate the dead window where dispatches sit `queued_not_yet_claimed`. `startRunnerWatchdog` re-checks every root every 5 s (opt out `GM_MCP_RUNNER_WATCHDOG=0`), so recovery does not wait for the next dispatch. No `status.json` means never swept: that is registration, not a liveness verdict.
- **Dead-daemon pre-flight.** A ticket written into a dead spool waits unclaimed, and the spool cannot say "nobody is listening", so `daemonNotRunning` runs before `publishSpoolRequest`. A stale heartbeat gets one `ensureSpoolRunnerRunning` plus `DAEMON_START_GRACE_MS` (15 s); only then does the call return `error: daemon-not-running`, unwritten. It does not fire with no `status.json`, inside `daemonBootGraceActive`, or during `runner_update_in_progress`, where a stale heartbeat is expected and the dispatch must go through. `GM_MCP_DAEMON_PREFLIGHT=0` bypasses it.

## Dispatch wire and polling

- **Glob filters are validated here and forwarded untouched.** `codesearch` and `grep` read `glob`, `path_glob`, `include`, `exclude_glob` and `exclude_globs` as a string or array of strings; the wasm matches them (`!` excludes, `{a,b}` brace lists work, aliases merge). `withGlobFiltersCoerced` trims entries and fails loudly on a non-string/non-array value, an empty string, an empty array or a blank entry. Never join an array into one brace glob: that mangled entries containing `,`/`{`/`}` and refused `!`. The wasm sets `glob_matched_no_files: true` when nothing matches.
- **Waited dispatches disclose it.** A reply landing after `DISPATCH_WAIT_DISCLOSED_AT_MS` (5 s) carries `dispatch_waited_ms`, so queue time shows on success too. `codesearch` `timeout_ms` is a scan wall-clock budget (regex default 20000) enforced in the wasm; its overrun reply is `timed_out: true`, `exhaustive: false`, `budget_ms`.
- **Timeout prefix sync.** `TIMEOUT_MS_PREFIX_LINE` mirrors the rs-plugkit `strip_timeout_ms_prefix_directive`: skip leading whitespace; the first line must start with `timeoutMs=` or `timeout_ms=`. Keep the two in sync.
- **Instruction hash assertion.** `deliveredInstructionHashByOwner` caches, per (project root, `session_id`), the hash of the `instruction` prose last returned to that caller. `withAssertedInstructionHash` asserts it on the next `instruction` dispatch, so gm can answer `instruction_unchanged: true` instead of resending tens of kilobytes. The cache is process-lifetime and keyed on session as well as root: a restarted server resends the prose rather than inherit an assertion it cannot honor.
- **Poll budgets.** `pollTimeoutMs` computes the requested budget, not what the daemon enforces. An explicit `timeout_seconds` wins. Otherwise an exec body starting with `timeoutMs=<ms>` requests that plus 5 s (never under 120 s), because the daemon kills the child tree at its wall-clock `timeoutMs` and answers `exec_timeout`. A wrapper-injected prefix follows the poll budget minus 5 s, floored at 300 s (`EXEC_DEFAULT_LIMIT_SECONDS`) and capped at 900000 ms (`EXEC_HARD_CEILING_MS`). A poll without a prefix waits 120 s; a `resume_task` poll has only `timeout_seconds`. Every poll is capped at 600 s (`GM_MCP_POLL_TIMEOUT_CEILING_MS` overrides). A timeout reports requested and applied budgets and why it ended; it neither cancels nor republishes.
- **A timed-out dispatch still answers.** `timeoutReply` reads each diagnostic alone, so a throwing one is dropped, never the resumable task; `npm run verify-build` fails when one cannot be built.
- **Exec output envelope.** `unpackExecOutputEnvelope` parses the `data` JSON string before cleaning, so `stdout`, `stderr` and `result` keep their own 16000-char cap (`EXEC_OUTPUT_FIELD_TRUNCATE_AT`) instead of the 400-char cap of the packed string. The marker names `result_file` (set when a field exceeds 2000 chars) or, for an older daemon, the out-file. A structured `result` is capped by compact JSON length only when `result_file` is present.
- **Hand-written JSON.** `normalizedObjectBody` (`dispatch.js`) passes a non-object string through as raw text; an escape-looking parse error gets a repair hint naming the escape.
- **Spool reads.** Symlinks are refused before open; the opened file is checked by dev and ino, never by a `/proc` or `/dev/fd` path (`dispatch.js`). Stale response files are pruned at most once per `SPOOL_PRUNE_EVERY_MS`, and `reclaimLockByRename` lets only the rename winner own a reclaim.
- **Alias fields are per handler.** `git_reset` reads `ref|rev` and `mode|hard`; `git_revert` reads `ref` alone, so a `rev` alias is silently ignored (`verb-table.js`).

## Response compaction

- **Two stages.** In `src/response-compact.js`, `cleanResponse` is lossless housekeeping: it strips opaque ids, drops empties except the answer lists in `EMPTY_LIST_IS_THE_ANSWER_KEYS` (an empty `candidates` prints `[]`), and truncates prose with a pointer at `LONG_TEXT_FIELD_TRUNCATE_AT` (400 chars). A plain-text-body verb (`isPlainText` in `dispatch.js`) gets `PLAIN_TEXT_OUTPUT_INLINE_MAX` (32768, read once from env at start), because its whole response is the script's output; raising the generic cap would un-truncate `instruction`'s prose. `fs_read` gets `FILE_READ_INLINE_MAX` (65536): at 400 chars every whole-file read became a pointer and callers fell back to host reads. `max_chars` overrides the defaults.
- **Full response.** `full_response: true` bypasses cleaning, data flattening, native-envelope decoding and wire compaction, so every guest field and layout survives; the response file stays bounded by the 4 MiB read limit. Exec-family fields keep `EXEC_OUTPUT_FIELD_TRUNCATE_AT` and `result_file`. Default responses keep actionable `dispatch_id` evidence; `request_fingerprint` is omitted by default and kept in full responses.
- **Failures are not compacted.** Compaction runs only when the response has no failure. Faults keep their diagnostics, except that default responses omit `stdout` when it is a nonempty JSON object deeply equal, field for field, to the containing fault object; the response names the original spool file.
- **Field decisions.** Dropped: `route_hint`, `reply_hash`, `orient_nouns`; `supply_chain_scan` when it has no findings (else `warnings` capped at 8 with `warningsOmitted` beside `warnCount`); `session_owner_before_this_dispatch` unless `session_mismatch` is true. Collapsed to counts: `codeinsight_overview`, `codeinsight_start` (to `{ready: true}`; whole when not ready), `config_changed` (newest transition, 3 keys), `dream_rsi_strategy`, `dream_rsi_replay`. Excerpted: row and hit prose in `ready_wave`, `prd_items`, `mutables_pending`, `recall_hits` (top 4), `bm25_hits`, `vector_hits` (top 20 each, codesearch channels); `id`/`key`/`status`/`session_id`/`verb` are exempt so a row stays addressable. Codesearch's `bm25_hits`, `vector_hits` and `commits` stay as named channels even when empty (`[]`), so a dual reply always shows all three; `WIRE_OMITTED_WHEN_EVERY_ROW_IS_ALREADY_IN` only fuses rows that carry a `key`, which dual rows never do. Kept whole: `instruction`, `phase`, `ok`, `session_id`, `instruction_hash`, `policy_hash`, `discipline_policies` (only when the policy hash moved), and every count.
- **Count mode.** Wire compaction of count results requires explicit `ok: true`, `exhaustive: true`, no failure or partial diagnostics, and same-length exact `path:count` parity between `output` and structured `counts`. Only the derived `output` is omitted; count rows, totals and scan metadata stay whole.
- **Phase history and receipts.** `phase_history` is context, not a gate decision: the wire keeps its newest five transitions in source order with retained/total counts. Current phase, session mismatch and pending-work counts stay whole. Committed `git_commit`/`git_finalize` successes keep at most five received `excluded` and `excluded_but_dirty` examples; the metadata counts received examples, not native totals. Failures, refusals, uncommitted receipts and `full_response: true` bypass this.
- **Zero hits.** A search reply with no hits is annotated `zero_hits_is_not_a_finding` unless the scan covered its files (`searched_zero_files`): "0 hits" and "code absent" are identical bytes.

## Working directory, sessions and dev sync

- **Cold projects.** A non-git cwd is rooted on itself (`projectRootFor`) and the daemon registers and sweeps it like any project, so it needs no `git_root_override`. First claims on cold projects are slow under a shared daemon; the timed-out note says so and points at `resume_task`.
- **Plain-text ownership.** Plain-text replies carry a byte-zero `gm_session_id=<owner>\n` header before the timeout directive; the guest advertises `gm_session_header_version: 1`. MCP probes with a safe JSON `phase-status` and caches only a coherent result bound to project, daemon boot, PID and GM hash; every nonempty pool slot must agree, and a new hash or mixed pool invalidates it. Legacy or unverified guests get the original text with `owner_transport: legacy-unverified` or `unverified`; nothing is retried.
- **In-flight count.** `inflightDispatchCount()` feeds the exit and signal records, the self-update check (`deferred-dispatch-inflight`) and the runner-swap signal (`dispatch-in-flight`). A bundle swap waits for dispatches too, because a failure during a dispatch looks like a network stall. A process quitting mid-dispatch strands the spool ticket it wrote, and nothing polls for its reply. A deferred self-update is retried seconds later, up to 4 times per trigger (`self-update-defer-retry`, then `self-update-defer-retry-exhausted`), so a server busy at one hourly tick still refreshes inside that hour instead of waiting a whole interval; the retry runs the same check, so the `.checked` stamp and `GM_MCP_SELF_UPDATE_INTERVAL_MS` still govern how often anything is fetched.
- **Cwd-less dispatch never guesses.** The root comes from the `cwd` argument, then `GM_MCP_DEFAULT_CWD` or `CLAUDE_PROJECT_DIR`, then the server cwd only when it is a git toplevel (or `GM_MCP_ALLOW_PROCESS_CWD=1`); otherwise the reply is `error: cwd-required`. A shared server launched from $HOME once wrote state into $HOME/.gm while the caller's spool stayed empty.
- **Leases.** `ensureAgentLease` attaches a project by writing `<agentplugDir()>/leases/<key>.<pid>.lease` with the project root, once per project and pid. The daemon-side rule (it watches a project only while a lease exists) is not verifiable here.
- **Layout cache.** `git-adapter.js` caches only `rev-parse` layout questions (`LAYOUT_QUESTION_FLAGS`); gating reads such as `status --porcelain` are never cached.
- **Dev sync.** `runDevSync` syncs the parent before its submodules, because the parent's `--ff-only` merge moves submodule pins; a submodule fast-forwards only when on `main`. `maybeStartDevSync` never blocks a dispatch: the child is detached and unref'd, stamps are written before the spawn, and one sync starts per 10 minutes (`SYNC_INTERVAL_MS`) across all roots.

## Process resilience and diagnostics

- **Stdio never exits on errors.** `keepServingOnAsyncFailure` (uncaught, unhandled, stdin and stderr errors) and `surviveClientGone` (stdout EPIPE, stdin end) record and continue. A dispatch is a spool ticket someone waits on; exiting would turn a recoverable stall into a dead session. Each stdout error code is recorded once.
- **Signal and exit records.** `logSignalExits` records SIGINT, SIGTERM, SIGHUP and SIGBREAK, then exits 0, so the exit status hides the signal; the `exit` record carries it. That record in `src/transport-guard.js` also carries `uptime_ms`, which survives the repeat filter (it ignores `pid`), so two servers exiting with the same code in one window each leave a line. A killed singleton leaves no `exit` record, because `logSignalExits` only sees signals a handler runs for.
- **Stdout guard.** `isJsonRpcFrame` checks that the first byte is `{` before parsing, since every stdout write passes through it and a response can be about 1 MB. Anything else is diverted to stderr as `stdout-write-diverted`.
- **Diagnostics.** `appendDiagnostic` writes each record to stderr and, unless repeat suppression holds it, to `logFilePath()` (`gm-mcp-server.log`, rotated to one `.1` past 2 MB by `src/server-log.js`). An identical event and fields within 60 s are counted, not written (ignoring `ms`, `inflight`, `dispatches_inflight` and `pid`), and the next write of that key is preceded by `repeat-suppressed`. The host discards stderr, so the file is the durable record.
- **Runtime-only logs.** `gm-mcp-server.log` and `dev-sync.log` (`src/dev-sync.js` `logPath()`, one JSON line per sync run, under `agentplugDir()`) live outside the repository. Nothing reads either back.

## HTTP transport and singleton

- **Singleton is opt-out.** One shared server per machine, keyed by port. `httpSingletonEnabled` (`src/singleton.js`) is off only when `GM_MCP_NO_HTTP_SINGLETON` or `GM_MCP_HTTP_SINGLETON_OFF` is set to anything but `0`/`false`/`no`/`off`. An agent host registered with the HTTP url never launches this server, so with nothing listening its connection fails for the whole session and every gm tool is absent. Hence the default is on: a stdio session relays to it (`serveStdioRelay`, `src/stdio-relay.js`) and starts no watchers; only an opt-out or unreachable singleton falls back to a local server with watchers (`stdioRelayTarget`). `gm-mcp dispatch` seeds one awaited with `wait: false` (`src/cli.js`), since dispatch runs with no MCP client and doubles as the revival path. `ensureHttpSingleton` trusts the health probe on the port over the state file (`gm-mcp-http.json`), which is only a hint. The spawned singleton runs the bundle this process launched from (`launchedEntryPath`), not whichever `gm-mcp` resolves first, and inherits `GM_MCP_NO_HTTP_SINGLETON=1`: seeding inside the singleton would spawn a server on the port it already holds.
- **Supervisor.** `ensureHttpSupervisor` (`src/singleton.js`) spawns one detached, unref'd sibling per port that probes `/health` on a timer and reruns the start path when answers stop, so a dead server returns without a human. Detached, because a caller-parented supervisor dies with the caller's tree. Opt-out: `GM_MCP_HTTP_SUPERVISOR=0`, for the same reason as the singleton. An HTTP-transport process arms it, and `ensure-http` arms it on every run. The child inherits `GM_MCP_HTTP_SUPERVISOR=0`, or every server it restarts would arm a second supervisor. `runHttpSupervisor` runs in the foreground so a service manager can hold it. Spawns are claimed per port by `claimSpawn` (`wx` create); losers answer `claim-held` or wait for health. Liveness is the state file's `ts`, refreshed each pass and stale after `SUPERVISOR_STATE_STALE_MS` (60 s), not its pid: a recycled pid would leave the port unwatched for good. `supervisorToKeep` (`src/singleton.js`) keeps a fresh claim's pid, else the newest start time; equal start times keep neither, because retiring the wrong one leaves the port unsupervised.
- **Instance registry.** Each HTTP-transport process registers in `<agentplugDir()>/gm-mcp-http-instance-<port>.json` (`recordHttpInstance`): pid, bundle version, entry path and the supervisor pid it armed. The port is the instance key, so a second `GM_MCP_HTTP_PORT`/`--port` is a second instance. `registeredHttpPorts()` enumerates instance files, supervisor files and `gm-mcp-http.json`. `sweepHttpInstances()` runs in `ensure-http` and on every supervisor pass:
  - `reapDeadHttpInstances` drops all three files of a port whose server is gone, so the number is reusable.
  - `replaceBehindHttpInstances` retires a server whose `/health` version is behind this process's `BUNDLE_VERSION` (`versionBehind`) and starts a fresh one on the same port, so an attached session reconnects to current code.
  - `reapOrphanedHttpInstances` stops one with no live supervisor, a provably dead parent (`parentPidOf`) and zero established connections (`establishedConnectionCount`). A null answer (the platform cannot say) and any nonzero count are never reaped.
  A version replacement also stops that port's supervisor, or the old one would respawn the old bundle, and re-arms it with `ensureHttpSupervisor({force:true})`, since a supervisor carries `GM_MCP_HTTP_SUPERVISOR=0` in its env and would otherwise answer `disabled`. `ensureHttpSingleton` applies the same version test to its port and retires a recorded pid that holds the port but answers no health check.
- **Stateless transport.** No session id is issued; every POST builds a fresh server and transport (`serveStatelessMcpRequest`), because the SDK rejects a second request through one transport. Non-POST requests to `/mcp` get 405. `startHttpServer` records `http-listen-failed` with the errno `code` before rethrowing, since stderr is discarded by the host.
- **Protocol version.** After `initialize`, the SDK answers 400 to an `mcp-protocol-version` outside `SUPPORTED_PROTOCOL_VERSIONS` (SDK 1.30.0, `validateProtocolVersion`). `normalizeProtocolVersion` rewrites the header to `SUPPORTED_PROTOCOL_VERSIONS[0]` before the SDK reads it; without that, a current client's calls get 400 and the server looks dead.
- **Supervision outside this repo.** The singleton on 8787 is detached and unref'd, so nothing in this tree restarts it; a client that POSTs straight to the port (a shell bridge such as `gmc.py`) gets `ECONNREFUSED` once it dies. `scripts/install-autostart.mjs` fixes it: it writes a managed block into `$HOME/beforestart` (boot) and `$HOME/crontab` (`@reboot` plus a minutely `ensure-http` guard), runs `ensure-http` once, probes `/health` first, and is idempotent. Reinstall: `node scripts/install-autostart.mjs`; uninstall: `--uninstall`; dry run: `--check`. Manual revive and status: `node ~/.gm-tools/gm-mcp-server.mjs ensure-http` / `http-status`. Guard log: `$HOME/logs/gm-mcp-autostart.log`; server log: `gm-mcp-server.log`.
- **Body cap and listen retry.** `readCappedJsonBody` counts bytes as they arrive (Content-Length alone lets chunked bodies through). `EADDRINUSE` is retried until the listen deadline, with or without an adopted handle (`http-transport.js`).
- **Staleness is never silent, and is said once.** `/health` carries a `bundle` block (`running_version`, `running_sha256`, `installed_version`, `installed_sha256`, `stale`, `reloadable`, `refusal`); `gm-mcp http-status` prints it. A dispatch reply that is not file content or a paged spill file carries one line naming both versions, once per installed bundle (`bundleStalenessNotice`; a new installed sha re-arms it). `fs_read`, `result` and `gm_result` are excluded because their replies are handed back byte for byte.

## Child reaper and attribution

- **Attribution gates reaping.** `child-ledger.js` rows name the dispatch that spawned each pid. Only attributed exec children are candidates (`DEFAULT_LEAK_KINDS = ['exec']`); the spool runner, http server and supervisor are detached on purpose. A stdio server is spawned by its MCP client, so it has no ledger row: `liveMcpClientInParentChain` judges it from the host process table, and an unreadable ancestor is unmeasured (null), never no-client.
- **Verdict.** `verdictOf` answers `unknown` if any predicate is unmeasured (null), `keep` if any fails, and `retire` only when all pass.
- **Parent and browser predicates.** `parentAbandoned`: a dead parent is abandoned; on win32 a live parent never is; on POSIX pid 1 or 2 counts. A browser whose command line has `--user-data-dir` belongs to a lane; without it, it is the user's own and protected.
- **Unmeasured is not absent.** `portListenerState` (`ports.js`) answers `measured: false` for an invalid port and `hasListener: null` when unmeasured; only a measured answer licenses retiring a port.

## Self-update and release channel

- **Any running copy keeps the deployed bundle current.** `src/self-update.js` refreshes the deployed `gm-mcp-server.mjs` under `GM_TOOLS_DIR`/`~/.gm-tools` from the release channel whichever copy runs the check, and the result carries `self`, true only when the refreshing process is that file. A dev checkout or a `src/`/`bin/` run therefore updates a deployment it is not: a machine whose long-lived server was started from the repo build no longer strands the deployed copy behind upstream (measured: `bin/gm-mcp-server.js` on `main` at 0.2.63 while the deployed copy sat at 0.2.60 because no process ever ran from it). `GM_MCP_SELF_UPDATE_DEPLOYED_ONLY` set to anything but `0`/`false`/`no`/`off` restores the older rule that only the deployed copy's own process refreshes it, reported as `not-deployed-copy`, and a missing deployed copy is reported as `no-deployed-copy` instead of being created behind the operator. Handover is a separate question: `refreshStaleDeployedBundleInBackground` calls its `onRefreshed` only when `result.self === true`, because a repo-build process handing its listen handle to the bundle it just installed would reload into bytes it is not running. The fetch runs after `server.connect`, so the 30 s connect window is never delayed; the new bundle serves from the next connect unless the transport hands over in-process (see "Bundle drift and handover"). Therefore `bin/gm-mcp-server.js` on `main` is the live release channel: a pushed drifted bundle reaches every deployed copy within an hour.
- **A bare swap silently undoes a lost fix.** The 2026-10-04 build lost `windowsHide: true` on 1 of 3 child-spawn sites. Three guards gate `replaceDeployedBundle`, mirroring the runner's:
  - Freeze: `GM_MCP_NO_SELF_UPDATE` set to anything but `0`/`false`/`no`/`off`, or `gm-mcp-server.no-self-update` in `$AGENTPLUG_HOME` (else `~/.agentplug`), checked before the fetch.
  - Local-build pin: `gm-mcp-server.local-build.json` (sha256, path, version, ts), refused while the installed sha256 matches; written and cleared by the `pin-local-build`/`unpin-local-build` subcommands in `src/cli.js`.
  - No downgrade: `BUNDLE_VERSION` (`src/bundle-version.js`) is compared numerically per component, so 0.10.0 beats 0.9.0.
  Each refusal returns `outcome: 'refused'` with a `code` and logs one stderr line naming the reason, since the check runs in the background. Bumping `BUNDLE_VERSION` is part of every deploy: a release that keeps the installed version is refused everywhere. The version is read from the candidate's bytes, so keep the `BUNDLE_VERSION = "x.y.z"` assignment recognizable to `BUNDLE_VERSION_ASSIGNMENT`. `scripts/build.mjs` derives that banner from the source version, and `verify-build` checks the updater parser against it before checking byte drift. CI checks out with `fetch-depth: 0` so `scripts/check-version-bump.mjs` sees the pushed range.
- **The release channel can be asked for now, not an hour later.** The hourly tick defers while `<deployedPath>.checked` is fresher than `GM_MCP_SELF_UPDATE_INTERVAL_MS` (1 h), so a fix pushed upstream reached the machine up to an interval later -- measured 2026-10-15: a fix pushed at 19:47 had not landed an hour after, and an agent that pushes and keeps working reads the OLD bundle and can conclude its fix did not land. `src/cli.js` therefore exposes `self-update-now`, which runs `refreshDeployedBundleNow` (`src/self-update.js`): the same `refreshStaleDeployedBundle` with `ignoreStamp`, so the stamp-freshness deferral is the ONLY thing it skips -- freeze, local-build pin, no-downgrade, `same-build`, the shebang/size/`node --check` loadability gates and the inflight-dispatch wait all still hold, and it arms no retry timer and calls no `onRefreshed`, so a one-shot run beside a server holding 8787 starts nothing, binds nothing and signals nothing. It records the same `self-update-check` diagnostic with `forced: true` and prints `previous -> new` version plus `describeSelfUpdateOutcome(result)`, which names the reason nothing moved for every other outcome. The hourly path is untouched: `refreshStaleDeployedBundle` alone still defers on a fresh stamp.
- **Out-of-band controls.** Four operator-set off controls gate self-update: the freeze, the `GM_MCP_SELF_UPDATE=0` switch (`refreshStaleDeployedBundle`), `GM_MCP_SELF_UPDATE_DEPLOYED_ONLY`, and the local-build pin. The release channel cannot write them. The fetch URL (`GM_MCP_BUNDLE_URL`, else `DEFAULT_BUNDLE_URL` on raw `main`) is the publisher's own, so a publisher-side compromise passes every guard except the operator-set ones.
- **Release bridge (`src/release-bridge.js`).** Runs on every stdio connect and HTTP start, at most once per 10 minutes (state in `gm-mcp-release-bridge.json` under `AGENTPLUG_HOME`; `GM_MCP_RELEASE_BRIDGE_INTERVAL_MS` overrides, `GM_MCP_RELEASE_BRIDGE=0` disables). It upgrades the installed `agentplug-runner` and `gm.wasm` from the latest `AnEntrypoint/agentplug-bin` and `plugkit-bin` releases. Integrity is the published `.sha256` sidecar alone: it proves the bytes match the published sidecar, not who published them. The runner is taken only when `--build-info` reports a release build at exactly the tag's version; `gm.version` is written as bare semver. Each swap renames the installed file to a `.bak-<from>-<stamp>` sibling and deletes none. The freeze env vars, the freeze files (`gm-mcp-server.no-self-update`, `agentplug-runner.no-self-update`) and a runner local-build pin are honored. A non-semver `gm.version`, a `gm.local-dev-sideload.json` marker, or a `gm.build.json` whose `origin` is not `"release"` marks a sideload and is never overwritten. After a swap it sends SIGTERM to the daemon in `daemon-status.json` when its owner lock, where present, names the same pid (on Linux the pid must be an `agentplug-runner` image) and it does not already report the new sha; a dispatch in flight defers the signal into the state file. The gm client's watchdog respawns the runner.
- **Release records.** `recordRunnerSwap` writes `agentplug-runner.version` and `last-completed-runner-swap.json` (version and sha256); the daemon's parity reader is outside this repo, so that parity is unverified here. `recordGuestBuild` writes `plugins/gm.build.json` with `source_sha` from the release body's `source-head:` line. Release assets are accepted only from `https://github.com/<repo>/releases/download/`.

## Bundle drift and handover

- **A process runs its launch bytes.** Node reads the bundle once and nothing re-reads it, so a newer bundle installed over `~/.gm-tools/gm-mcp-server.mjs` (by a lane build, `dev-sync`, anything) reaches a long-lived server only through a reload. Two triggers exist: `refreshStaleDeployedBundle` (release channel, hourly, file against URL) and `startBundleDriftWatch` (`src/bundle-drift.js`, every 30 s, file against this process's bytes). The release-channel check answers `current` whenever file and URL agree, whatever this process runs, so alone it never picks up a hand-installed bundle; the drift watch covers that gap.
- **Drift measurement.** Drift is measured against `launchedEntryPath()` (cached by size and mtime, so the 1 MB hash runs only when the file moved). `bundleDrift()` answers `stale` on a hash difference and `reloadable` only for a single-file bundle whose `BUNDLE_VERSION` is not older than the running one. `no-downgrade`, `installed-version-unknown` and `running-not-a-bundle` (a dev checkout would restart on every edit) report staleness and refuse the reload. `GM_MCP_BUNDLE_DRIFT_RELOAD=0` disables reloads and keeps the reporting.
- **Stdio reloads by relaying, not exiting.** Exiting would detach the client, because its `StdioClientTransport` closes on this child's `close` event. `handOverStdioToRefreshedBundle` (`src/bundle-refresh.js`) spawns the installed bundle as a child on its own pipes, then in one synchronous step drops the SDK transport's `data` listener from `process.stdin` and pipes stdin to the child and the child's stdout to `process.stdout`, so exactly one reader owns the frames. MCP stdio frames are newline-delimited JSON, so the relay copies bytes and parses nothing. The child is adopted only once its stderr carries `connected, serving on stdio`; a dead child clears the relay and the next tick hands over again.
- **HTTP reloads hand over the socket.** `handOverToRefreshedBundle` (`src/bundle-refresh.js`) spawns the new bundle with an IPC channel, sends the listening `net.Server`, and stops accepting only once the child answers `gm-mcp-handover-ready`. The child adopts it with `server.listen({ handle })` from the raw `_handle`. Both processes hold the socket, so nothing goes unanswered during the switch. Close-then-bind is the fallback when the ready reply never comes, and `takePortBack` re-listens if the replacement never answers `/health`.
- **Reloads never cut work.** Nothing starts while `inflightDispatchCount() > 0` (`bundle-handover-deferred`, retried next tick), and the outgoing process waits for that count to reach 0 before `process.exit(0)`, so a reply being written finishes.
- **Stdin drain.** `drainAndExit` waits for the dispatch count and open connections to reach 0 before `process.exit(0)`; the stdio relay detaches the SDK listeners by identity and pauses stdin.

## Verbs, witnesses and probes

- **Verb list.** The verb set is one table in `src/verb-table.js`. `RUNNER_REGISTRY_VERBS` in `src/verbs.js` is derived from it, and `runnerVerb(row)` is the only place the runner's hyphen spelling is produced. Each entry is a `gm.<verb>` binding inside the single registered MCP tool `gm_codemode` (`src/codemode.js`), named by `verbToolName` (hyphens become underscores). A verb missing from the list has no `gm.<verb>` binding. `VERB_TABLE` derives from `REGISTRY_ROWS` in row order, and `verbDescriptionLead()` opens every verb description, which `gm.list()` strips.
- **CI name.** `verify.yml` is named `build-verify` on purpose; that AnEntrypoint/gm's bump-pins holds on this name is external and unverified here.
- **Witness and probe scripts.** `scripts/pool-observe-served-witness.mjs` checks the served client's pool-observe output against the candidate contract in rs-plugkit `crates/plugkit-core/src/orchestrator/pool_rank.rs`. `test/mcp-http-probe.mjs` and `test/http-session-resume.mjs` are manual probes outside `npm test`; the second defaults to port 8791, leaving the singleton on 8787 alone.
- **Reaper test.** `test/leak-reaper.test.mjs` spawns real orphans; run it alone with `node test/leak-reaper.test.mjs`. `test/leak-reaper-processes.test.mjs`, `test/leak-orphans.test.mjs` and `test/leak-watch.test.mjs` pass a synthetic process table and a stub `signalPid`, so they never signal a live process; the orphan tests additionally pass a stub `readProc`, so they never read a live `/proc` either.
- **Leak watch is the only automatic caller of `reap`.** `src/leak-watch.js` runs on the hourly scheduler in `src/self-update.js` (`scheduleStaleDeployedBundleChecks(onRefreshed, hourlyPass)` — no second timer per process), reads the host process table once and shares that one table across the census, the reaper's unattributed pass and the supervisor duplicate count. A notable pass writes a `leak-watch` diagnostic and one stderr line; a clean one writes nothing. `gm-mcp-server.js leak-watch [--apply] [--json]` runs the same pass by hand. Env: `GM_MCP_LEAK_WATCH=0` disables the pass, `GM_MCP_LEAK_POPULATION_WARN=<n>` moves the population threshold (default 8), `GM_MCP_LEAK_AUTO_APPLY=1` arms auto-retire.
- **Orphans are the leaks the ledger cannot see.** `src/orphan-scan.js` rides the same pass and the same single table read (no second timer): a candidate is a pid whose `ppid` is `1`, that no `child-ledger` row claims, that is heavyweight (`GM_MCP_LEAK_ORPHAN_RSS_MB`, default 150 MB) and idle — CPU seconds over seconds alive below `GM_MCP_LEAK_ORPHAN_DUTY` (default 0.02) — after `GM_MCP_LEAK_ORPHAN_MIN_AGE_MS` (default 900000, 15 min) alive. 11 reparented runners took 3367 MB of a 7.8 GB box on 2026-10-15 at ~0.01 duty while the one live run kept burning CPU, so the duty ratio is the discriminator, not age. It reports `orphans` and never signals: gm did not spawn an orphan, so gm does not classify whether it may be killed — there is deliberately no `GM_MCP_LEAK_ORPHAN_AUTO_APPLY`. `GM_MCP_LEAK_ORPHANS=0` disables it. Each orphan root also gets a `trees` entry (one per `items` entry, same order): its descendants, walked through the `ppid` field of `/proc/<pid>/stat`, bounded at depth 16 and 512 members, so one leaked tree is one finding with a member count and a root-inclusive RSS total, and a descendant is never counted as an orphan itself. `truncated` names the bound that cut a walk. The ppid index is read once per pass, and only when a root exists.
- **The orphan scan reads `/proc/<pid>/stat` and `/proc/<pid>/status`, never `ps`.** A `ps` on a box loaded enough to grow orphans can take over 120 s and time out, so rss, threads, state and CPU ticks come from `/proc` per candidate pid only; mac and Windows have no `/proc`, so the section is empty there instead of quietly reporting a number it never measured. The `comm` field of `stat` may hold spaces and parens, so the numeric fields are counted from the LAST `)`: index 0 after it is field 3, which puts utime at 11, stime at 12 and starttime at 19.
- **Auto-retire is narrower than the reaper's `retire` verdict.** It applies to `unattributed-server` findings of transport `stdio` only, and `autoApplyDecision` adds guards the reaper does not make: not the pid answering `/health` or owning a registered port, no live MCP-client ancestor, no live-session ancestor, a measured start time at least `DEFAULT_MIN_RETIRE_AGE_MS` (30 min) old, and at most `DEFAULT_MAX_AUTO_RETIRE_PER_PASS` (3) per pass. A process whose ancestry cannot be read, or whose age cannot be measured, is never signalled — an unmeasured null is never read as "old".
- **Classify before retiring by age.** `liveSessionNameOf` (`src/process-table.js`) names the desktop and session managers that look exactly like multi-day orphans (`selkies`, `xfdesktop`, `xfce4-session`, `s6-svscan`, `Xvfb`, ...); a candidate with such an ancestor is exempt. Counts come from that shared table matched on each row's own argv, never from a `pgrep -f` pattern, which matches the counting shell itself.
- **Population is bounded by a warning, not by a kill.** `populationOf` compares the gm-mcp process count against the threshold; RSS is not part of it because the shared table carries no rss. Duplicate `http-supervise --port <N>` supervisors are counted by `duplicateSupervisorFindings` and left to the existing `retireDuplicateHttpSupervisors` sweep (`GM_MCP_HTTP_SUPERVISOR_DUPE_REAP`). The orphan scan is the one place rss is read, and it reads it per pid from `/proc/<pid>/status` rather than from the shared table.
- **Stale probe expectations.** `test/http-session-resume.mjs` expects a 200 GET heartbeat carrying `retry:` and an `http-empty-body-ignored` event. Current `src/` answers GET with 405 and emits no such event, so those checks do not match this build (not run).

## Architecture decisions

### ADR-GMMCP-SELFUPDATE-1: the self-update guard compares build identity

- **Status.** Accepted by the user. Implemented in `src/self-update.js` `versionGuardReason(candidateBytes, installedBytes)`: a candidate older than the installed version is refused (`no-downgrade`), a byte-identical candidate is refused (`same-build`), and an equal-version candidate with different bytes is eligible.
- **Context.** `scripts/check-version-bump.mjs` demands a `BUNDLE_VERSION` bump per `src/` change, and the strictly forward no-downgrade test refuses an equal-version candidate whatever its bytes.
- **Decision.** The guard compares build identity, the candidate's build stamp and bytes against the installed bundle, and not the version string alone. A same-version candidate with a different build identity is eligible. This is the repo rule for self-update guards (root `AGENTS.md`, Implementation rules).
- **Consequences.** An equal-version release stops being refused by the version test. The windowsHide regression (see "A bare swap silently undoes a lost fix") is not a version question, so the freeze and the local-build pin remain the controls.
